# 2026 AI Agent 应用工程师 · 应用层八股清单

> 整理日期：2026-11-10
> 来源：面灵AI《155 道 Agent 真题》（截至 2026-09）、265 道大模型+Agent 合辑、掘金《AI 应用开发 100 道全套八股》、GitHub RAG 面经汇总、牛客字节 Agent 岗面经、多篇公众号面经复盘。
> 用法：先看第零节和第 12 节的优先级分层，别从头背。带「必背」的自测能不能讲满 60 秒；带「加分」的知道概念就行；带「可跳」的直接放弃。

## 零、2026 和 2025 的差别（先看这个，决定你背什么）

**三句话概括变化：**

1. 前年问「什么是 Agent」「ReAct 怎么实现」，2026 一开口是「Harness 怎么设计」「上百个 Skill 怎么管理」「越权调用怎么监控」。这些概念半年前很多还不存在。
2. **概念题只是敲门砖**——几乎每道架构/工具/记忆题后面都跟一句「你们项目里具体怎么做的」。只背定义，追问里必露馅。
3. 越来越爱问**「怎么量化」**——幻觉率怎么定义、提升的百分比用哪个测试集算的。简历上每个数字都要能说清口径。

**必须能画出来的三层包含关系：**

```
Prompt   ⊂   Context   ⊂   Harness
对指令的工程化  对输入环境的工程化  对整个运行系统的工程化

Agent = Model + Harness
Harness = Agent − Model      ← 除了模型本身，其余决定它能否稳定交付的都属于 Harness
```

## 一、Agent 基础与架构（必背，100% 会问）

| 题 | 答题框架（60 秒） |
|---|---|
| 用大白话说什么是 Agent，和 Siri 类助手的边界在哪 | Agent 能自己决定「下一步做什么、用什么工具」，Siri 是固定意图槽位填充。差别在**决策权归谁** |
| 为什么要用 Agent 而不直接调大模型 | 大模型只会输出文字，缺实时数据、缺私有数据、不能执行动作。Agent 补的是「手」和「眼」 |
| Agent 和 Workflow 的关系，怎么选型 | 流程固定 → Workflow（可控、便宜、可测）；路径不可预知 → Agent（灵活、贵、不可测）。**判断依据是「分支能不能枚举完」** |
| 常见 Agent 架构模式 | ReAct（边想边做）/ Plan-Execute-Replan（先规划再执行，失败重规划）/ Reflection（自我批判迭代）/ 多 Agent 编排 |
| ReAct 是什么，工作流程和优缺点 | Thought→Action→Observation 循环。优点：每步可解释、中途可改主意。缺点：步数多则 token 和延迟涨、容易绕圈。**落地要加步数上限 + 重复调用检测** |
| ReAct vs Plan-Execute-Replan | ReAct 短视、适合探索型任务；PE 有全局视野、适合步骤多且依赖链长的任务。PE 需要监管 Agent 是因为**规划本身会错，需要有人判定「这步结果算不算达成」** |
| 最小可用 Agent 是不是一个 ReAct Loop | 不是。除循环还要有：工具契约与白名单、上下文管理、终止与异常、可观测（轨迹留存） |
| 三种方案怎么选：单次 Prompt / Workflow / Agent | 一次调用能解决 → Prompt；步骤固定但多 → Workflow；步骤取决于中间结果 → Agent。**成本差 10 倍以上，默认从便宜的开始** |
| 企业落地 Agent 最大瓶颈 | 不是模型能力，是**可靠性**：错误会链式放大、效果不可测、成本和延迟不可控、权限边界难划 |
| Agent 和传统后端项目的架构差异 | 多了模型服务层（路由/降级/限流）、上下文与记忆层、编排层（DAG 调度）、评测与可观测层。**不确定性要当成架构一等公民** |

**高频追问：** 「你们项目里 Agent 和 Workflow 是怎么分的？」「为什么不用纯 Workflow？」——要能举一个你自己项目里的具体场景。

## 二、Harness / Context / Prompt 三层（2026 新增，中大厂必问）

这一节是 2026 年才热起来的，考察理解力不是背诵。

| 题 | 答题框架 |
|---|---|
| Prompt / Context / Harness Engineering 三者区别（钉钉） | 包含关系，边界一层比一层大。Prompt 管指令，Context 管「这一轮给模型看什么」，Harness 管「整个系统怎么持续、可靠、可控地跑」 |
| Agent Engineering 和 Harness 分别指什么 | Agent Engineering 是搭 Agent（选框架、写工具、设计流程）；Harness Engineering 是搭**它周围的运行环境**：循环、工具、上下文、权限、校验、恢复 |
| Harness 做的事 LangChain 一直在做，为什么现在火了（字节三面） | 以前框架解决「怎么搭起来」，现在模型能力够了，瓶颈变成「怎么稳定交付」。**框架是开发期便利，Harness 是运行期控制** |
| 主流开源 Harness 有哪些 | Claude Code、Codex、OpenCode、DeepSeek Harness 都属于 Harness（模型 + 循环 + 工具 + 上下文管理 + 权限） |
| 你了解 Claude Code 的上下文管理吗（快手/蔚来） | 三层：CLAUDE.md（常驻规则）→ 工具结果按需读取（不是全塞）→ 阈值触发压缩/重置，把状态写成 artifact 交给新会话 |
| LangChain 和 LangGraph 区别（字节/快手/阿里） | LangChain 是**链式**（线性、无环、状态靠变量传）；LangGraph 是**图 + 显式状态**（支持环、条件边、检查点）。状态快照靠 checkpoint 存每步 state，可断点续跑 |
| 为什么 Java 生态选 Spring AI 而不是 LangChain4j（京东/字节） | Spring AI 贴合 Spring 生态（自动装配、Bean 管理、Actuator 监控），团队迁移成本低；LangChain4j 更贴近 Python 版语义但生态弱 |

**这一节的杀手答案（背这段）：**
> 「Harness 就是 Agent 减掉模型。模型负责推理，Harness 负责给它手和眼，并且保证它不会跑偏——工具白名单、上下文注入、权限边界、失败恢复、结果校验，都算 Harness。所以同一个模型，Harness 好坏能差出一倍的效果。」

## 三、工具调用四件套：FC / MCP / Skills / A2A（最高频，必背）

这是 2026 出题最密的一块。四个词**不在一个层面**，答错层级直接露怯。

### 3.1 一句话定义（先背这个）

| 概念 | 一句话 | 类比 |
|---|---|---|
| **Function Calling** | 给模型一份工具说明书（名字/参数/类型），让它学会**开口要**工具；真正执行的是你的代码 | 会打申请单 |
| **MCP** | 把「接工具/接数据」标准化，M×N 集成变 M+N | USB-C 统一插座 |
| **Skills** | 把「干某类事的整套流程 + 知识 + 脚本」打包，**按需加载**（渐进式披露） | 施工手册 |
| **A2A** | Agent 与 Agent 之间怎么发现彼此、委派任务、跟踪进度 | 跨部门协作流程 |

### 3.2 必背题

| 题 | 要点 |
|---|---|
| Function Calling 原理？模型怎么知道调哪个工具（阿里/快手/京东） | 把工具的 JSON Schema 和问题一起发；模型输出 `tool_calls`（name + args）；你的代码执行；结果以 `role=tool` 追加；再请求一次。**模型不执行，只点单** |
| 参数格式不对怎么处理（阿里） | `json.loads` 包 try → 错误信息当 Observation 回灌让它自己改；**校验顺序要先查未知键再查必填**，否则模型不知道是键名写错 |
| MCP 是什么，解决什么问题（字节/腾讯/京东/阿里） | 标准化客户端-服务端协议。工具方做一次 Server，应用方实现一次 Client。解决 M×N 集成地狱 |
| MCP 底层原理，和传统 Tool 注册区别（阿里） | JSON-RPC over stdio/SSE/HTTP。支持**动态能力发现**（ListTools）和标准化调用（CallTool），不用提前硬编码 |
| MCP 与 Function Calling 区别（字节/快手/货拉拉/百度） | **不同层**。FC 是模型能力（怎么表达），MCP 是接驳协议（怎么连）。MCP 最终调用仍走 FC 那套机制 |
| MCP 通信方式有哪些（阿里） | stdio（本地进程）/ SSE（HTTP 长连接，旧）/ Streamable HTTP（新标准） |
| MCP 会不会过时，为什么热度降了（阿里千问） | 协议本身在沉淀，热度降是因为**大部分场景用 bash + API 调用更简单**，MCP 的收益在「跨客户端复用」。别硬吹 |
| MCP 和 Skills 区别（几乎全员问） | MCP 解决「接得上」，Skill 解决「做得好」。Skill 内部可以调多个 FC、用 MCP 接来的工具 |
| Function Call / MCP / Skill 三者边界（B站） | 原子动作（FC）→ 连接标准（MCP）→ 业务能力包（Skill） |
| 为什么 Skills 能省 token（网易/快手/腾讯） | 渐进式披露：启动只加载 name + description（约 100 token），命中才展开全文 |
| 渐进式披露怎么实现，为什么要这么做（美团） | 元数据 → SKILL.md 正文 → references/scripts 三层。实测初始上下文从 16k 压到 500 token 量级 |
| 上百个 Skill 怎么管（快手） | 检索（按描述召回）→ 分层（域/子域）→ 渐进式披露。**别全量塞进 prompt** |
| 大规模工具集下怎么降低工具幻觉、提升选对率（字节/快手） | 工具描述写清「什么时候该用/不该用」、按场景分组、先选组再选工具、加参数校验 |
| 工具报错/无响应/连续失败的策略（快手/蔚来） | 重试（指数退避）→ 熔断 → 降级（换工具/换路径）→ 上报人工。**要有超时，不能只靠模型自觉** |
| 如何决定哪个 Agent 能访问哪些 MCP | 按最小权限原则，Agent 身份绑定 MCP 白名单，平台侧统一授权 |

### 3.3 追问杀手：「那它们冲突吗？」

> 不冲突，能套娃。一个 Skill 内部可以调若干个 Function、用 MCP 接来的工具。四层是**地基 → 接法 → 上层封装 → 跨 Agent 协作**。

## 四、记忆与上下文工程（必背，出题密度第二）

| 题 | 要点 |
|---|---|
| 短期记忆和长期记忆怎么实现、怎么区分（京东/携程/美团） | 短期 = 当前会话消息列表（有窗口上限）；长期 = 外部存储（向量库/结构化库/文件），靠检索召回注入 |
| 记忆模块选什么数据库，选型依据（京东/滴滴） | 语义召回 → 向量库；结构化事实（用户偏好、画像）→ 关系库/KV；时序对话 → 文档库或日志。**多数项目是混合** |
| 长期记忆和 RAG 的区别（阿里千问/通义） | 机制同构（都是检索注入），差别在**写入者**：RAG 写的是文档，记忆写的是交互中沉淀的事实。记忆多了「该不该写」和「何时遗忘」两个问题 |
| 记忆怎么召回，怎么避免相互污染（字节） | 按会话/用户/任务打 namespace 隔离 + 时间衰减 + 相关性阈值。**不同问题的记忆不能进同一个池子混召** |
| 上下文压缩放链路哪一步，先压缩再向量化还是反（字节） | 先压缩再向量化（压缩后语义更集中）；但**对检索无用的历史才压，原始 chunk 不压** |
| 长对话怎么处理，滑动窗口+摘要怎么落地（字节/腾讯） | 保留最近 N 轮原文 + 更早的做摘要 + 关键事实抽成结构化槽位。摘要要保留实体和数字，别只保留叙述 |
| 工具调用结果怎么压缩（字节/蔚来） | 大结果卸载到文件/存储，只回传引用 + 摘要；小结果原地截断。**别让小模型二次摘要，会失真** |
| 为什么上下文越长结果越不稳 | 注意力稀释 + 中段信息被忽略（lost in the middle）+ 指令冲突。所以关键指令要放头尾 |
| 快到窗口阈值怎么避免打断体验（字节） | 异步压缩、后台预压缩、超阈值时才切，且切点选在任务边界 |
| 除了压缩还有什么方案，大结果卸载怎么做（字节/蔚来） | 卸载到文件系统，给模型一个 read_file 工具按需取；或用 RAG 方式回捞 |
| 多轮长任务怎么避免「目标迷失」（字节） | 把目标写成结构化 state 每轮重述；用 Plan 做锚点；阶段性复述验收标准 |
| 怎么区分上下文污染和工具污染（字节） | 上下文污染 = 模型被历史误导；工具污染 = 工具返回内容本身错/脏。**看换新 session 后是否恢复** |
| 记忆有没有量化指标 | 记忆命中率、召回准确率、任务成功率对比（开/关记忆的 A/B）。**没有公认指标，能说清口径比指标本身重要** |

## 五、多智能体协作（中厂以上必问）

| 题 | 要点 |
|---|---|
| 多 Agent 相比单 Agent 的优势（阿里/美团） | 上下文隔离（各管一摊不互相污染）、能力专精、可并行。代价：通信开销、错误传播、调试难 |
| 常见协作模式 | 主从（Supervisor）/ 流水线（Pipeline）/ 辩论（Debate）/ 群聊（Group Chat）/ 层级（Hierarchical） |
| 子 Agent 怎么通信，串行还是并行（美团/快手） | 结构化消息（JSON/Markdown）+ 统一 schema。并行适合无依赖子任务，串行适合有依赖。**并行要有超时和部分失败容忍** |
| 主 Agent 怎么动态选子 Agent（美团） | 两派：路由（按能力描述分类，快但粗）/ 规划（先出 plan 再派发，准但慢）。生产多用「粗路由 + 子 Agent 自评能否胜任」 |
| 多个 Agent 结论冲突怎么办（京东） | 投票/加权/仲裁 Agent/回退到人工。**关键是要有裁决机制，不能靠最后一个说话** |
| 主 Agent 怎么知道子 Agent 完成（蔚来） | 同步等返回 / 异步回调 / 轮询状态表。异步要有 task_id 和状态机 |
| 多 Agent 怎么完全隔离（字节/蚂蚁） | 上下文、权限、存储三层隔离。跨 Agent 共享走显式传参，不共享全局状态 |
| 怎么防止任务拆分阶段的错误一路传播（字节） | 拆分后先做「计划校验」（另一个模型或规则检查），执行每步做「结果验收」，失败可回退到拆分 |
| 多智能体真能提效吗，怎么证明（字节） | 必须做 A/B：同任务单 Agent vs 多 Agent，比成功率、耗时、token 成本。**很多场景多 Agent 只是更贵** |
| 中心化 vs 去中心化调度 | 中心化易观测、易回退、有单点；去中心化抗故障但难调试。调研类任务多用中心化 |

## 六、评估、幻觉与安全兜底（2026 明显加重）

| 题 | 要点 |
|---|---|
| Agent 评测体系包括哪些维度（阿里） | 任务成功率 / 步骤效率（步数、token）/ 工具调用正确率 / 幻觉率 / 延迟 / 成本 / 可恢复性 |
| 怎么衡量 planning 能力和 hallucination rate | planning：给定任务看计划是否覆盖必要步骤、有无冗余（可用 LLM-as-judge + 人工抽检）；幻觉：答案中的无依据陈述数 / 总陈述数 |
| 怎么构建 Agent 评测体系（Shopee/小红书） | 建 test set（含正常/边界/对抗）→ 定义可自动判定的 rubric → 跑回归 → bad case 归档 → 每个改动跑全量 |
| 幻觉率怎么定义和计算（字节） | 分母是答案中的事实性陈述条数，分子是无检索依据/与库冲突的条数。**必须报口径，否则数字没意义** |
| 智能体死循环的原因和方案，为什么要三层（字节/快手） | 原因：工具失败反复重试、目标不可达、格式反复错。三层：**模型层（prompt 约束）→ 循环层（重复检测 + 步数上限）→ 系统层（超时、熔断、兜底输出）** |
| 怎么设计机制终止无效循环，不只靠最大轮次（字节） | 检测重复 (tool, args) 指纹、检测「连续 N 轮无新增信息」、检测目标是否已达成、成本预算上限 |
| 生产环境四类典型故障（字节） | 思考链错误传播 / 工具幻觉（编造调用）/ JSON 格式崩坏 / 无限循环。分三层解：prompt+校验（第一道）、解析容错（第二道）、兜底降级（第三道） |
| 线上一直调工具但不返回，怎么 Debug（字节/腾讯混元） | 看轨迹：是工具持续失败、还是模型判断不了该收尾。**先看每次工具返回，再看模型每轮 thought**。区分 Prompt / 模型 / 工具 / 逻辑四类问题靠「替换变量法」 |
| 可观测性怎么建（通义） | 轨迹留存（每轮 prompt/输出/工具结果）、指标（步数、延迟、token、失败率）、回放（能重跑同一轨迹） |
| Prompt Injection / 间接注入怎么防（钉钉/小红书） | 输入侧关键词+分类器过滤；结构上把外部内容标为「数据不是指令」；工具侧白名单 + 高危操作人工确认；输出侧校验 |
| 沙箱怎么实现（B站） | 容器隔离 + 只读挂载 + 网络白名单 + 资源限额 + 快照回滚 |
| 权限怎么控制，高危操作怎么限（腾讯/京东） | 最小权限 + 分级审批（读自动、写需确认、资金类双人）+ 操作审计 + 金额/数量硬上限 |
| HITL 触发时 Loop 什么状态，怎么暂停恢复（蔚来） | 状态机里的 waiting_approval 态，state 持久化（checkpoint），审批后从该点续跑 |
| 中间出异常怎么断点恢复（字节） | 每步 checkpoint 存 state + 已完成步骤 + 中间产物；恢复时从最近 checkpoint 重放，幂等操作要打标 |
| 怎么区分「内容过时」和「模型幻觉」（字节） | 过时 = 有来源但源旧（查文档时间戳）；幻觉 = 无来源或与来源矛盾（查引用） |

## 七、RAG（应用岗必考，和 Agent 一起问）

**完整链路（必背，一环都不能漏）：**
```
文档加载 → 解析清洗 → 分块 chunk → Embedding 向量化 → 索引存储
→ 检索召回（向量 + BM25 混合）→ 过滤 → Rerank 重排 → 上下文组装 → 生成 → 评估
```

| 题 | 要点 |
|---|---|
| RAG 完整流程，哪个环节最影响效果 | 链路如上。**瓶颈通常在切片和检索策略，不在模型**——召回差，生成必然飘 |
| RAG 相比微调的好处，怎么选 | RAG 改知识不动权重、可溯源、更新便宜；微调改风格/能力/格式。**多数先 RAG，确有必要再微调** |
| RAG 怎么缓解幻觉，原理 | 把事实从「模型记忆」换成「检索依据」，缩窄生成空间；配合 prompt 约束只依据检索内容 + 阈值拒答 |
| 切片粒度怎么选，切断上下文怎么办 | 通用 256–1024 token、重叠 10–20%。结构化文档（合同/条款）用**结构感知切分 + 父子块**：检索用子块，合成时带上父块 |
| Embedding 模型怎么选，维度怎么选（快手/腾讯/京东） | 按语种/领域/是否自托管选；bge-m3 多语、bge-large 中文强。维度越高表达力越强但存储和检索成本涨，**不是越高越好** |
| 向量库选型：Milvus / ES / HNSW / IVF_FLAT（字节/美团/快手） | 规模大、要高性能 → Milvus（HNSW/IVF）；已有 ES 且要混合检索 → ES；小规模 → FAISS/pgvector。HNSW 查得快、内存高；IVF 省内存、要训练、召回略低 |
| 能不能用 ES 做向量库，怎么混合检索（京东/钉钉） | 能（dense_vector + kNN）。混合 = BM25 与向量各自召回后融合 |
| 混合检索怎么评估，权重怎么设，RRF 的 K 调大还是调小（京东/美团） | 权重用验证集网格搜；RRF 的 k 越大越平滑、越削弱头部差异，**k 调小更看重 top 名次** |
| 为什么需要 Rerank，什么情况可以不接（京东/快手） | 召回用 Bi-Encoder 快但粗，Rerank 用 Cross-Encoder 精算相关性。候选少或延迟极敏感可不接 |
| 双向量召回 vs 单向量召回 | 双向量（query 两路改写各召一次）提升召回但成本翻倍 |
| Query 改写 / 问题拆分的意义（携程/美团） | 用户问句口语化/多意图，改写补全上下文、拆分多子问题。HyDE 是先让模型编一个假答案再拿它去检索 |
| 怎么评估 RAG 效果，评测集哪来（字节/阿里/京东） | 检索：Hit Rate、MRR、Context Precision/Recall；生成：Faithfulness、Answer Relevancy。评测集从真实日志+人工标注，几十到几百条起 |
| 回答错了怎么定位是检索还是生成（钉钉） | 先看检索结果里有没有正确答案：有 → 生成问题；没有 → 检索/切片问题 |
| 多路召回冲突怎么定 top，RRF 怎么融合三路（字节） | RRF 按排名倒数求和，不依赖分数量纲，天然适配多路 |
| 召回 30 条但只能放 6 条怎么取舍（字节） | 按 rerank 分排序 + 去重（同源去冗余）+ 保证多样性 + 关键实体必留 |
| 带权限的知识库，先过滤还是先召回（字节/蚂蚁） | **先 ACL 过滤再召回**（在检索条件里带权限位），否则会有越权召回和"答案泄露在候选里"的风险 |
| 知识库增量更新，瓶颈在哪（字节/快手/美团） | 解析和 embedding 最耗时；用变更检测 + 只重算变更块 + 异步队列 |
| GraphRAG 和 Agentic RAG（快手） | GraphRAG 用实体关系图做多跳推理，适合「跨文档关联」问题；Agentic RAG 让 Agent 自己决定检索几次、检索什么 |
| RAG 服务降级怎么设计（京东） | 检索超时 → 降级为纯生成 + 明示无引用；向量库挂 → 降级 BM25；都挂 → 兜底话术 |

## 八、工程细节（应用层的真功夫，中小公司特别爱问）

这一块不是"八股"，但**是最能证明你真做过的地方**。

| 题 | 要点 |
|---|---|
| 流式输出为什么用 SSE 不用 WebSocket | 大模型是服务端单向持续推流，WebSocket 的双向能力用不上还多出心跳和连接管理成本；SSE 基于 HTTP，网关接入和鉴权更顺 |
| SSE 落地三个坑 | ① 关掉 Nginx/网关的缓冲，否则不实时；② HTTP 200 发出后状态码改不了，错误要通过自定义事件传；③ 要在流式过程中做 token 统计和计费 |
| 前端怎么处理粘包半包 | 维护 buffer，按双换行分割，残缺 chunk 留在 buffer 等下次；TextDecoder 解码 |
| 为什么不用原生 EventSource | 不支持 POST、不能自定义 Header 传 token，改用 fetch + ReadableStream |
| 流式时怎么实时统计 token 并计费 | 每段用统一 tokenizer 累计；中断/异常也按实际消耗记账；终态落库 |
| 流式过程中模型断连怎么兜底 | 保留已输出内容 + 推错误事件 + 支持一键重试（复用原上下文） |
| 内容安全实时截断怎么做 | 边输出边过敏感词检测，命中即停止推理、清理上下文、推拦截事件、前端清空已渲染内容 |
| 多模型路由与降级怎么设计 | 按任务复杂度/成本/延迟路由；主模型超时或报错降级到备选；再降级到小模型或模板回答 |
| 限流、并发、排队 | 令牌桶限流 + 并发队列 + 优先级；长任务异步化 + 结果推送 |
| 成本怎么控 | prompt 压缩、结果缓存（精确 + 语义）、小模型分流、上下文复用（前缀缓存） |
| 模型选型怎么比 | 成本 / 延迟 / 效果 / 数据合规 / 可控性五维，用你自己的评测集跑，别看榜单 |

## 九、手撕代码（应用岗必考一种）

**Agent 特色的（2026 新高频，优先练）：**

1. **脱离框架手写最小 ReAct Agent**——工具注册、循环控制、终止条件、异常处理四块。这是 2026 下半年新出现的高频题，应用岗尤其常考。（详见 `interview/mini_agent_interview.py`）
2. 手写上下文压缩 / 滑动窗口摘要（给定消息列表和 token 上限，决定保留、摘要还是卸载）
3. 手写完整工具调用链路：解析参数 → 校验 → 执行 → 回传
4. 手写多 Agent 消息路由器（按角色/能力分发，处理超时和失败重试）
5. **手写死循环检测器**：给定调用轨迹 calls（含 tool 和 args），最近 window 次里同工具同参数出现 ≥k 次即判死循环

**通用算法（照常考，难度中等）：**

- 链表：反转、相加、排序链表
- 二叉树：层序遍历、右视图
- 数组/字符串：接雨水、无重复字符最长子串、字符串解码 `k[encoded]`
- Top-K（快速选择 vs 堆，要能说复杂度）
- 前缀树（Trie）及应用场景
- 大数相加（字符串模拟）

## 十三、三个能加分的"独有细节"（你手上就有）

别人背不出来的东西，比多背十道题值钱：

1. **「模型会自己编 Observation」**——你实测过 qwen2.5:7b 在 Action Input 后擅自写 `Observation: 8.33`，所以必须设 `stop=["\nObservation:"]`。这是 ReAct 落地最常见的 bug，官方资料叫 stop-token footgun。
2. **「中文检索不能用 split 切词」**——你踩过：整句当关键词 → 0 命中 → 模型搜一次就说没找到、直接放弃。改成字符 bigram 覆盖度才对。
3. **「协议不是成败关键」**——你做过 2×2 消融：工具描述和工具实现两个变量缺一都是 0/3，都修好后手写 ReAct 也能 3/3，bind_tools 只是快 2.5 倍。**能拿数据反驳"用了框架就更强"的候选人很少。**

## 附：一句话总纲（被问懵时用来稳场）

> Agent 就是把「决策」交给模型、把「执行」留在代码里的一套约定。模型只会输出文字，所以所有工程问题最终都归结为三件事：**怎么让它说清要什么（工具契约）、怎么让它不跑偏（上下文与约束）、怎么在它跑偏时兜住（循环与降级）。**
