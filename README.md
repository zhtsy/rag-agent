## 它是干什么的

往一堆自己的文档里提问，它答得出、答得对，而且每句话后面都能点回原文；库里没有的，它就说没有。

这个项目是从一句很具体的抱怨开始的：**为什么问它文档里的东西它答不上来，却敢一本正经地编？**
后来越做越发现，难的不是让它答得出，是让它在该闭嘴的时候闭嘴。所以一半以上的时间
其实花在评测和排查上——`CASE_STUDY.md` 记的就是几次被自己的数据打脸的经过。

## 结论

| 看什么 | 结论 |
|---|---|
| 48 题主评测集 | **1.0000**（48/48）。最早 38 题是 0.9474 —— 提分来自补 18 条图边，**提示词一个字没改** |
| 10 题对抗集 | **1.0000**（10/10），含 4 道「库里没有」的拒答题全对 |
| 自动化测试 | 本地 **477 passed / 1 skipped**（17 秒）；云端容器内同版本；CI 只装 pytest，约 2 秒 |
| 多轮记忆 | 16 轮窗口 + 滚动摘要；灌 18 轮后仍能答出第 1 轮埋的编号（摘要压到 49 字，实体全保留） |
| 性能（单机 2 vCPU） | 有实体过滤 3.68 s；同问缓存命中 0.86 s（4.3×）；并发饱和点 4 |
| 数据规模 | 生产索引 145 块 / 741 实体 / 882 条关系；实验索引 **3,196 块**（合成多格式，12.8）与 **7,082 块**（真实法律语料，12.9–12.10） |

## 它不擅长什么（先说清楚，省得你试完再失望）

- **域外问题它可能还是会答。** 检索层能正确判空、把 `sources` 置空，但模型有时仍会用
  自己的常识答一段，`status` 会标成 `ungrounded`——**标得出来，但没拦住**。
  硬拒答会把「资料没写但能推理」的题一起打死，我选了留这个洞并写在明处。
- **只为私有小语料设计。** 现在的分块、图谱抽取、重排都是按几百张文本卡片调的，
  换成十万级文档要改架构，不是调参能解决。
- **单机吞吐就 0.8 req/s 左右。** 并发 4 是实测饱和点，超了只是排队更久。

## 几个绕不开的取舍

这五条是整套设计里真正被数据逼出来的决定，其它都能改，这几条改不动。

1. **检索入口只有一个。** 图谱查不出东西就自动降级到向量 + BM25，不让模型自己挑工具——
   它挑错的时候，你在日志里看不见。
2. **没有证据就不答。** rerank 原始 top1 低于 0.15 直接返回「未在知识库中找到相关信息」，
   并把 `sources` 置空。实测 OOD 问题 ≤0.05、正常题 ≥0.6，中间没有重叠带。
3. **置信度不是「答对的概率」。** 它只是 rerank 分数，用来判「检索有没有落空」；
   拿它当业务阈值一定会出事。
4. **拒答和答对同等重要。** 补数据把准确率从 0.9474 拉到 1.0000 时，4 道拒答题
   没有一道退化成乱猜——这条对照比 1.0000 本身更有说服力。
5. **图谱的坑通常在数据，不在查询。** 有 2 道题长期答不出，不是提示词写错了，
   而是 `(城市)-[:属于]->(省)` 这条边从来没建过。完整闭环见 `CASE_STUDY.md`。

> 指标口径与采集时间见 `RESULTS.md`；三 seed 波动见 `VARIANCE.md`；
> 本地复刻云端的完整流程见 `MIGRATION.md`。

## 4. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 服务信息 |
| GET | `/health` | 健康检查，返回 `{"status","inflight","limit"}`（并发水位） |
| POST | `/chat/stream` | **主接口**，SSE 流式。请求体 `{"message": "...", "session_id": "...", "user_id": "可选"}`。**需鉴权**；过载时 **429** |
| POST | `/feedback` | 提交 👍/👎，含 `contexts` 证据字段。**需鉴权**（匿名可达等于谁都能往数据飞轮里灌垃圾，归因直接失真） |
| GET | `/feedback/stats` | 反馈分布统计。**需鉴权** |

> ⚠️ **没有 `POST /chat`**。所有客户端必须用 `/chat/stream`，否则 404。

### 并发闸门（429）

同时在跑的流式请求数有上限，默认 **4** —— 这是 `PERF.md` 实测的**饱和点**：
2 vCPU 上再往上加，吞吐不再增长，只是每个请求都变慢（`rerank` 是唯一随并发
翻倍的一段，929ms → 1848ms，因为它是纯 CPU，抢不到 LLM 那段 I/O 的空闲）。

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `RAG_MAX_CONCURRENT` | `4` | 同时进行的流式请求上限 |
| `RAG_QUEUE_WAIT` | `8` | 排满后最多等多少秒，超时回 429 |

**语义是"快速失败"而不是"无限排队"**：等 8 秒还轮不到，说明已经过载，
让用户拿一个 429 比拿一个 40 秒后的答案更有用。429 响应带 `Retry-After: 5`，
前端会提示"请约 5 秒后重试"。

实测（16 并发同发）：

```
codes Counter({200: 14, 429: 2})
inflight max 4          ← 服务端并发从未超过上限
latency [2.7, 3.2, 4.7, 5.8, 6.8, 8.0, 8.3, 8.8, 10.2]   ← 排队可见
```

`/health` 里的 `inflight` 就是为了让这件事可观测：排满时接口**仍然是 200**，
只看 `status: ok` 会以为一切正常。

### 鉴权（`/chat/stream`）

必须带密钥，否则 **401**（未配置密钥时是 **503**）：

```bash
curl -N -X POST http://127.0.0.1:8000/chat/stream \
  -H 'Content-Type: application/json' \
  -H "X-API-Key: $(cat .rag_api_key)" \
  -d '{"message":"小陈养了什么宠物？","session_id":"cli"}'
```

- 支持 `X-API-Key: <key>` 或 `Authorization: Bearer <key>`，两者等价。
- 密钥来源（优先级）：环境变量 `RAG_API_KEY` → `/app/.rag_api_key` → `./.rag_api_key`。
  统一由 `api_auth.py` 读取，前后端、评测脚本、MCP、健康检查共用同一个口径。
- **校验在进入路由之前短路**：错误密钥不会消耗任何模型额度。
- 密钥读文件（不缓存），**轮换不需要重启**：`openssl rand -hex 24 > .rag_api_key && chmod 600 .rag_api_key`。
- `GET /`、`GET /health` 保持开放（探活）；`/feedback`、`/feedback/stats` 同样要密钥，否则可被匿名刷日志。

SSE 帧格式：

```
data: {"text": "逐"}          ← 逐 token
data: {"text": "字"}
data: {"text": "（补充：…）"}   ← 完整性兜底追加（可能没有，见第 10 节第 5 条）
data: {"sources": [...], "confidence": 0.93, "status": "answered",
       "contexts": [...], "timings": {"rid": "...", "total_ms": 8894.1, "stages": {...}}}   ← 终帧
data: [DONE]
```

`timings` 是本轮的分阶段耗时（毫秒）：`decide` / `graph` / `retrieve` / `rerank` / `llm` / `finalize`，
`agent` 是整张图的总时间（≈ 各段之和）。前端可以据此显示"检索 0.5s / 生成 0.6s"，
离线统计 P50/P95 也不用手工埋第二套点。

`confidence` 只有一个口径（`confidence.compute_confidence`，`rag_agent` 只做转发别名），取值语义：

| 值 | 含义 |
|---|---|
| `null` | 本轮是**拒答**（知识库里没有就明说）。"置信度"这个量不适用，不是 0 分 |
| `0.0~1.0` | 本轮最相关那块证据的 rerank 分数，越高越贴题 |
| `0.5` | 拿不到 rerank 分（无度量），不要当成"中等把握" |

**拒答为什么给 `null` 而不是 `0.0`**：0 会被读成"系统答得很差"，但"知识库里没有马斯克"
本身可能是完全正确的回答。想知道拒答得对不对，看终帧的 `status`：

| status | 条件 | 含义 |
|---|---|---|
| `answered` | 有证据 + 正常作答 | 常规情况 |
| `out_of_scope` | 无证据 + 拒答 | 知识库本来就没有，**正常拒答** |
| `missed` | 有证据 + 拒答 | 检索到了却没答出来，**要排查** |
| `ungrounded` | 无证据 + 作答 | 没有依据还在答，**幻觉风险** |

**拒答怎么判**（`confidence.looks_like_abstention`，分两级；对应测试 `tests/test_confidence.py`）：
- **强词**（`无法从知识库`、`知识库中没有`、`图谱中没有`…）在**第一句或结论位（最后一句）**命中即算拒答。
  结论位必须认，否则"资料里没有直接写…所以无法从知识库中确定她住在哪个省"这种
  "先陈述后结论"的拒答会被漏判成正常回答（实测拿到 0.4457）。
- **弱词**（`没有说明`、`没有直接写`、`资料里没有`…）**只在第一句生效**。
  放全文会误杀"前半句答了主问题、后半句补充某细节没写"这类正确答案（历史踩过的坑）。

它是"对这条回答内容的把握"，**不是"答对的概率"**。要做质量监控请看 `/feedback` 的 bad 率。

**检索相关性门槛**：rerank 最高分低于 `RAG_MIN_RELEVANT`（默认 `0.15`）时判为检索落空，
直接返回"未在知识库中找到相关信息。"，**不下发任何来源**。没有这道门槛时，RRF 会把
无关块硬召回出来（问"马斯克是谁"实测 5 块最高分仅 `0.0026`），前端来源栏却挂着
`test2.txt / test3.txt`，看起来像那些文件里写了答案。

## 4.9 记忆（会话级 + 滚动摘要）

只做**同会话内**的记忆，不做跨会话的用户画像。取舍理由见本节末尾。

### 四层结构

| 层 | 存在哪 | 生命周期 | 作用 |
|---|---|---|---|
| 图状态 `messages` | 进程内存（`MemorySaver`） | 进程活多久 | 多轮对话、工具调用配对 |
| 会话实体 `_ENTITY_MEMORY` | 进程内存 + `chat_sessions.entities` | 跨重启 | 代词消解（"它今年几岁" → 代码） |
| 轮次原文 `chat_turns` | MySQL | 长期（可 purge） | 重启 / 换 worker 后回填最近 N 轮 |
| 滚动摘要 `chat_summaries` | MySQL | 长期 | 承载已经滑出窗口的旧轮次 |

**进程重启后怎么接上**：`stream_conversation` 先看进程里有没有该 thread 的状态；
没有就按 `session_id` 从 `chat_turns` 取最近 N 轮、从 `chat_summaries` 取摘要，
**拼在本轮输入前面**一起送进图。不用 `aupdate_state`——那个 API 会顺带决定
"下一个跑哪个节点"，空状态之外用它容易把新输入吞掉。

### 窗口：按 provider 动态

| provider | 历史窗口 | 依据 |
|---|---|---|
| `deepseek` / `hybrid` | **16 轮** | 云端 128K 上下文，16 轮 × (问 30 + 答 160) ≈ 3000 字，宽松 |
| `local` | **3 轮** | 本地 7B `num_ctx=2048`，3 轮 ≈ 570 字，再多就把检索证据挤出去 |
| 其它 / 未识别 | 8 轮 | 保守默认 |

写死一个数字是错的。原来一律 3 轮，等于"云端也按最坏情况跑"，用户问到第 4 轮就开始失忆；
现在只有真降级到本地才收回 3 轮。取值逻辑抽在 `memory_context.history_turns_for()`，
因为 `rag_agent` 一 import 就要加载 bge + reranker（1.2GB），在 CI 里没法测。

### 滚动摘要：让第 30 轮还知道第 1 轮的要求

```
第 1..N 轮 ──滑出窗口──> 后台压成摘要 ──> 拼在 system prompt 前
```

三个设计点，都是踩出来的：

1. **进度用 `chat_summaries.upto_turn` 记，只增不减**。没有它，每轮都会把同样的旧对话
   重复压一遍——既费 token，摘要还会越滚越长、越压越糊（每次从摘要再摘要，信息逐次衰减）。
2. **在 `finalize_turn` 里后台做**。摘要只影响"下一轮能看到什么"，这一轮已经答完了，
   塞进响应链就是让用户白等 1~2 秒。
3. **实体名兜底**。提示词里写十遍"保留人名"，模型仍会写成"主人的宠物是那只猫"。
   所以压缩完再用知识库实体词表扫一遍原文，缺哪个补到末尾 `【涉及实体】`。
   这是摘要最致命的信息损失：摘要读起来很通顺，没人会发现名字已经没了，
   而下一轮"它几岁"从此再也指代不了。

### 历史压缩的两条纪律

- **按句截断，不是硬切**：答案截到 160 字，尽量断在句末。`[:50]` 会把"搬到深圳"
  这类限定切掉，下一轮追问就答不上来。
- **整对丢弃**：历史 `ToolMessage` 与带 `tool_calls` 的 `AIMessage` 一起丢，
  否则会留下孤立的 `ToolMessage`，API 直接 400。

### 记忆存下来了，还得让模型敢用

记忆写进库不等于答得出来。踩过一个坑：灌到第 18 轮后问「我最开始让你记住的编号是几？只回数字」，
系统回「无法从知识库中找到相关信息」——**答案就在 49 字的摘要里，但它没被用上**。

排查发现跟记忆模块无关，卡在决策兜底：

```
决策模型直接抢答 "3"（没输出 tool_call JSON）
  → 旧逻辑：非严格 {"need_tool": false} 一律当"沉默" → 强制检索
  → 知识库里当然没有"我的编号" → 检索落空 top1=0.1484 < 0.15 → 拒答
```

顺带一提，那句抢答的 `3` 本身还是错的（正确答案是 1）。所以修法不是"采纳抢答"，而是：

1. **`decide_guard` 加规则 4**：会话里已有历史、且模型给出了实质内容时，视为「想直接答」，
   本轮不检索，交由生成阶段带历史/摘要重新组织。空内容、纯符号、`need_tool: true`
   仍然兜底检索。
2. **`has_context` 默认 `False`**：单轮（评测的全部形态）行为与旧版逐字一致，
   48 题基线不受影响。放宽只发生在真有多轮上下文的时候。
3. **提示词两条**：决策阶段禁抢答（"只回数字"约束的是最终回答，不是跳过判断的理由）；
   无资料提示词加一条例外——问题指向**本次对话本身**（我第一句问的是什么、我让你记的编号）
   时用对话历史回答，不算编造。

这条放宽是**必要的**：没有它，前面所有存库、摘要、实体兜底的努力，都会在最后一步被"没证据"
的指令一句话抹掉。

### 为什么不跨会话记用户画像

做过一版（`user_memories` 表 + 后台抽取 + 新会话注入），后来整块撤掉了：

1. **收益不如把同会话做深**。这是知识问答系统，用户很少需要"被记住是谁"，
   但几乎每个人都会连着问五六轮。同窗口的体验更直接。
2. **失败模式是"记错"而不是"记不住"**。实测把助手答案里的"小李"抽成了用户称呼，
   覆盖掉用户自己说的"张三"。这类错误用户看不见，纠错成本极高。
3. **会和检索抢位置**。画像一旦和知识库冲突，模型更愿意相信自己"记得"的事。

### 开关与运维

| 变量 | 默认 | 说明 |
|---|---|---|
| `RAG_MEMORY_STORE` | `1` | 关掉则完全不用持久化记忆（退化成纯进程内） |
| `RAG_MEMORY_EVAL_SESSIONS` | `0` | 评测会话（`eval-` 前缀）是否也落库。**默认关**，否则第二次跑分会带着第一次的历史，分数虚高 |

**会话隔离**：请求不带 `session_id` 时不再回落到全局 `default_session`
（那会让所有用户共用一个上下文），改为 `anon-` + 客户端指纹；同一台设备复用同一会话。

```bash
python memory_store.py stats                  # 会话数 / 轮次数 / 摘要数
python memory_store.py summary <session_id>   # 看摘要内容与已压到第几轮
python memory_store.py turns <session_id> 5   # 看最近 5 轮
python memory_store.py purge 30 --run         # 清理 30 天前的轮次（摘要保留）
```

**已知边界**：`MemorySaver` 仍是单进程的，多 worker 下每个 worker 首次访问同一会话都会
各自回填一次（内容相同不会错乱，只是多读一次库）；摘要只保留结论与实体，
细节（数字成立的条件、原文措辞）会在压缩中损失——这是摘要的固有代价，不是 bug。

`fix_source.py` 的匹配是三档递进，命中即停：

| T1 | 原样字面包含 | —（708 个） |

> **口径说明（引用分数前请先读这段）**
>
> 上面三个数都是**这一台云端机器**跑出来的，三个前提同时成立才有效：
>
> 1. **embedding 是 `bge-base-zh-v1.5`**，生成是 **DeepSeek**；
> 2. 评测集是**自己写的 48 条**（38 + 10），不是任何公开榜单，不可横向比较；

>

> 同一批题的分数**与上表不可比**（云端模型拉不开的差距会被小模型放大，反之亦然）；
> `pytest` 在本地是 **341 passed**（= 云端那 332 条 + 8 条 `test_lazy_graph` + 1 条文档一致性测试）。
> 所以报分请连**用例条数 + embedding 模型 + 生成模型 + 机器**一起报。

### 6.1 分层归因（`--layer-report`）

总分只说"丢了多少"，说不出"丢在哪一层"。而两者的修法完全相反：
漏召回要去补文档/调检索，召回但没写进去要去改提示词，多答要去加约束。
所以每条用例除了分数，还会算一次**归因**：

```bash
python3 eval_system.py --cases test_cases2.json --layer-report layer.md
```

报告明细里现在**存着本轮检索到的 `contexts`**（以前只存文件名，等于把唯一能定位
问题的证据扔了）。归因靠"关键词在不在证据里 / 在不在答案里"两个二值判断交叉得出：

| 在答案里 | 在证据里 | 归因 | 该改哪里 |
|---|---|---|---|
| 是 | 是 | `ok` | — |
| 是 | 否 | `ok`（`unsupported_hits` 会记下来） | 模型自身记忆，非检索功劳 |
| 否 | 是 | `generation_loss` | 提示词 / 选块顺序 / 上下文截断 |
| 否 | 否 | `retrieval_miss` | 召回 / 分块 / 图谱补边 |

两类特例**不许混进来**：

- **拒答类**（`category: 拒答`）：`must_contain` 是"未找到/无法"，本来就不该出现在
  证据里 → 归因记 `n/a`。否则 4 条拒答用例会全部变成"检索未召回"的假缺陷。
  但要是真把密码编出来了，仍然记 `violation`。
- **需要一步推理的用例**（用例里标 `"needs_inference": true`，目前是 T031/T032）：
  "南京→江苏"这类词按字面永远搜不到 → 记 `inference_miss`，语义是"证据够了、
  模型没走那一步"。**这个标记必须由出题人手写**，不许用启发式推断，
  否则真正的召回缺陷会被"这题需要推理"掩盖掉。

**实测结果（38 条，2026-11-05 那一轮，当时均分 0.9474）**：

| 指标 | 值 |
|---|---|
| 端到端均分 | **0.9474** |
| 检索召回率 | **0.9412**（34 条非拒答里，32 条的关键词都在证据中） |
| 三分归因 | 检索未召回 **0.00** ｜ 生成丢失 **0.00** ｜ 生成多答 **0.00** ｜ 未走推理 **2.00** |

**2 个丢分点没有一个是检索的锅**：只剩 `T031/T032`，是拒绝绝对域外做省外推（证据只写了“在广州/在南京”，答案要“广东/江苏”）。

> 这一轮之后的两件事让上表**变成了历史值**，别当当前基线用：
> T031/T032 已在 2026-11-06 通过补 18 条 `(城市)-[:属于]->(省)` 边消除（提示词一个字没动，均分 → 1.0000）；
> T028 的多答已在 2026-11-05 通过【铁律三】"只答被问到的那一项"修掉，跨主题分类 0.67 → 1.00。
> 也就是说"未走推理 2.00"现在是 **0**。**分层归因是定位手段，不是成绩单**——
> 它真正的价值是下面这条：两张表交叉出的 `retrieval_miss` / `generation_loss` 指向完全相反的修法。

检索召回率（`recall`）是**只看证据、不看生成**的指标，不随模型换说法而抖动，
比端到端分数更适合放进回归门禁。

> 报告里存了 `answer` 和 `contexts`，所以**改了用例标注不必重跑模型**。
> `merge_eval_reports.py --recases test_cases2.json` 会用最新标注重算归因
> （38 条重跑要 2-3 分钟，离线重算 0.1 秒）。

⚠️ 引用这里的分数请连**用例条数**一起报：早期 README 写过的 `0.99` 是 30 条小样本、
判据也更松，和现在的 38 条不可比。数字变小不是退步，是样本扩了 8 条且判据变严。

⚠️ 这台是**突发性能型**实例，CPU 积分耗尽时吞吐会掉到原来的 1/3：
`test_cases2` 全量一次约 153 秒，积分耗尽时会超过 320 秒还跑不完。
**低负载（`load` 0.0x）不等于不慢**，就是这个表现。
跑不完时用 `--offset` / `--limit` 分批：

```bash
python3 eval_system.py --cases test_cases2.json --offset 27 --limit 11
```

⚠️ `docker exec` 里被 `timeout` 或 SIGTERM 杀掉的 python **不会跟着死**，
会继续占 CPU 并往同一份日志里写，导致问句和答案错位（看起来像"跨题串台"）。
清理：容器里没有 `ps`/`pkill`，要扫 `/proc` 找 pid 再 kill。

**RAGAS 依赖**：基础镜像里没有 `ragas`，需要单独安装。建议在**一次性容器**里跑，
避免 pip 解析把 langchain 版本升掉、影响正在跑的后端：

```bash
docker run --rm -it \
  --network rag_deploy_default \
  -v "$PWD":/app -w /app \
  --env-file "$PWD/.env" \
  $(docker inspect rag_backend --format '{{.Config.Image}}') \
  bash -c "pip install -q ragas datasets && python run_ragas_eval.py"
```

## 7. 数据飞轮


> 归因就白做了。

## 9. 运维要点

**内存**：3G 物理内存 + 2G swap。`uvicorn` 常驻约 1.5-1.9G，neo4j 约 430M，mysql 约 320M。
**不要**在容器里跑会 import `rag_agent` 的脚本——那会二次加载 bge + reranker（约 1.5G），
和 backend 叠加就会 OOM（历史上发生过两次，会连带杀掉 `aliyun-service` 导致 SSH 断连）。
诊断一律走 HTTP 接口，或用不加载模型的脚本（`print_all_chunks.py` / `fix_source.py`）。

**CPU**：`ecs.e-c1m2` 是突发性能型实例，CPU 积分耗尽会降频，
rerank 单对打分从 0.35s 掉到 1.2-1.6s。**遇到"凭空变慢"先怀疑积分**，等几分钟再测。

## 10. 已知问题

1. **rerank 分不等于"能不能答"**：拒答判定不能拿它做阈值。实测答对的题可能只有
   0.18（"谁养了仓鼠"），答错的题也可能 0.99，两者分布重叠。
   现在的做法是：只用它度量"证据贴不贴题"，拒答交给检索层的"0 命中 + 无上下文"。
2. **图谱 source 覆盖率 97.3%（720/740）**：剩余 20 个是建图时归纳出的抽象概念
   （「水彩画」「海报设计」「游戏时长」等），知识库无对应原词，保持 NULL 是正确行为。
   历史上另有 12 个是写法变体（`Mcn机构`/`唱跳Rap`/`Npc房屋`），已由 T2/T3 匹配修掉。
3. **图谱关系类型被复用得过宽**：`住在` 既用于城市也用于"山坡/地下"（游戏文本），
   `属于` 既用于菜系归属也用于组织归属。对人的问题基本无影响，做全量推理前需要先规范本体。
4. **多实体比较问题不走图谱**：一条 Cypher 只能顺着一条路径查，实测会漏掉其中一个人，
   所以 ≥2 个实体的问题直接走混合检索。
5. **答案丢限定成分 → 已在检索侧修掉（不是提示词问题）**：
   现象是"小张养了什么宠物"偶发只答"布丁"、丢掉"仓鼠"。查下来根因**不在生成端**：
   - 该问题走图谱路径，模型现写的 Cypher 通常只有一跳 `(小张)-[:养了]->(布丁)`，
     而"布丁是什么"在第二跳。拼出的事实句就是"小张养了布丁"，**限定成分在检索层就丢了**；
   - contexts 是合成的图谱结果而非原文，所以答案再忠实也答不出来。

   修法（两道）：
   - `graph_retriever._enrich_entity_attrs()`：结果实体再补一跳归类属性
     （只认 `品种是/类型是/职位是`，**不含 `属于`**——它被复用得极宽，
     小刘属于校篮球队、片儿川属于杭州都在里面）。事实句变成`小张养了布丁（仓鼠）`。
   - `answer_guard.completeness_supplement()`：生成后确定性兜底，只认
     原文「叫X的Y」与图谱「X（Y）」两种句式，答案提了 X 却漏了 Y 才补一句
     `（补充：X是Y。）`；不满足就一个字不加。可用 `RAG_ANSWER_GUARD=0` 关闭。

   注意：`temperature=0.0` 下服务端仍有采样抖动，评测因此有 ±0.05 波动，
   **单次跑分不足以判定回归**，需多次取均值。

   补充（同一家族的第三个坑）：图谱里 4 个宠物有 2 个**根本没抽到类型边**——
   `小李-[:养了]->代码` 只有这一条边，而「代码」是一只橘猫（原文 test5.txt：
   "我养了一只橘猫，叫'代码'"）；`拿铁` 同理（test10.txt："一只叫'拿铁'的猫"）。
   检索侧补跳无从下手，只能修数据。已由 `fix_pet_types.py` 补齐
   （`代码→橘猫`、`拿铁→猫`，含新节点 source），脚本幂等、默认 dry-run，
   回滚见脚本头部注释。
6. **rerank 窗口砍太窄会直接把正确答案砍掉（曾经设 6）**：
   T019「加里奥为什么能吸收魔法」的 12 个候选里，含「禁魔石」的 3 块在 RRF 里
   排下标 6/7/8，全量 rerank 后最好的一块 score=0.4942、排第 5——本该进 top-5，
   却被 `docs[:6]` 截在门外，模型只能拿到 0.285 那块讲"魔法奥能"的，
   答案因此永远说不出「禁魔石」。
   实测稳态 0.39 秒/对，窗口 6→10 只多约 1.5 秒；8 与 10 的 top-5 完全一致，取 10 留余量。
   现为 `RERANK_MAX_CANDIDATES = int(os.environ.get("RAG_RERANK_CANDIDATES", "10"))`。
7. **选块曾用「关键词命中硬占 4 个名额」的写法**：`top_docs = priority_docs[:4]`，
   再从**另一个独立队列**补第 5 个 —— 第 5 高分块被丢弃，却用更低分的块填进来。
   T019 前 5 名全命中关键词，第 5 名（禁魔石 0.4942）被砍，换进来的是 0.285 的。
   现改为按 rerank 分数取前 5，关键词命中只加 0.05 倾向分，不做硬性名额。
8. **因果类问题的固有属性补不全**：`为什么/怎么/如何` 一律走向量检索，
   而"X 由什么制成"这类事实与问题的**字面相似度天然偏低**
   （"杜朗用禁魔石制作加里奥" 对 "加里奥为什么能吸收魔法" 的 rerank 分只有 0.138），
   靠相似度永远进不了 top-5。
   现由 `graph_retriever.entity_facts()` 直接从图谱取固有属性
   （`品种是/类型是/职位是/由...制成`，**仍不含 `属于`**），以
   `【来源：知识图谱属性】【确定性事实】` 的形式插在证据最前面。
   只对因果类问题生效；查不到就不注入，不硬凑。
9. **关键词匹配曾区分大小写**：用例写 `python`、模型答 `Python`，`python in answer`
   为假，T001 被误判 0.50。现 `eval_system.score_case` 统一按小写比较。
10. **T019 用例的 must_not_contain 自相矛盾（已修正）**：原为
    `["泰拉瑞亚", "德玛西亚人"]`，但它的 `expected_answer` 是
    "加里奥由禁魔石制成，禁魔石对魔法有很强的抵抗性" —— 而原文里禁魔石的来历
    本身就写在德玛西亚人故事线里（"只要有禁魔石障壁的保护，德玛西亚人就不会害怕魔法"），
    讲清禁魔石几乎必然出现该词。已移除过宽的"德玛西亚人"，保留"泰拉瑞亚"
    承担防跨主题串台的原始意图，并在用例里加了 `note` 记录原因。
11. **0 分题已归零（2026-11-06：靠补数据，不靠改提示词）**：
    - T031/T032「住在哪个省」：资料只说"住在南京"，模型不肯外推"江苏"。
      当时记的是"忠实性优先，暂不动提示词"——**判断是对的，但结论错了**：
      当时以为这是模型拒绝外推的取舍，真正缺的是 `(城市)-[:属于]->(省)` 这 **18 条边**，
      而 `graph_retriever` 的 Cypher 规则里早就写了「涉及省份必须走两跳 `住在→属于`」。
      **查询层的契约写好了，数据层从没满足过。** 补边即翻转，提示词一个字没动，
      4 道拒答题仍是 1.00——这条对照比 1.0000 本身更有意义：让系统答得出，没有牺牲"不乱猜"。
    - T028「最拿手的菜」：**已修，但要修两轮（2026-11-05）**。原来把几道川菜一起列出来、命中 must_not_contain。
      第一轮加“只答被问到的那一项”跑到 36/38，但**同一配置再跑一次回退到 35/38**——
      模型改用“虽然也擅长 A、B，但最拿手的是 X”的转折句式，表面上像补充说明，实际仍在罗列。
      第二轮把转折/递进句式明确禁掉、并划清“限定信息（同一件事的属性，要答）vs 同类条目（并列的其他对象，不答）”
      的边界后：T028 连跑 3 次都只答「开水白菜」。

    > 这套题是**自己写的 48 条**，`1.0000` 的含义是"在这套题上不再丢分"，不是"对任意问题都对"。
    > 真正可验证的是两条性质：**没有证据时不答**（4 道拒答题全对）、**每句话能指回出处**。
    > 这两个性质不随模型换说法漂移，比总分更适合当回归门禁。
12. **安全（已闭环）**：`/chat/stream`、`/feedback`、`/feedback/stats` 与管理端 `admin_app.py` 均要求 `X-API-Key`；
    5001 / 3306 / 7474 / 7687 全部绑定 `127.0.0.1`，对外只剩 8000 / 8501（远程看管理台走 SSH 隧道）。
    Neo4j / MySQL 口令已轮换为 32 位随机值并从 compose 移入 `.env`，旧口令实测已失效。详见 `OPS.md` 5.6。

13. **域外问题仍可能被「自己的常识」答掉（能检测，未消除）**：实测问「火星上有生命吗」，
    检索正确判空（`sources: []`），但模型仍会调训练知识作答，终帧 `status` 标为 `ungrounded`。
    这个状态值就是为它加的，但它只表示**被标出来了**，不表示被拦住了。
    没做成硬拒答是有意的：试过，一拦就把「资料里没写、但可以推理得出」的题也一起打死。
    所以被问「你怎么保证不乱答」时，正确的回答是——4 道拒答题满分只证明它在
    **有证据的边界内**可靠；域外仍有概率硬答，系统能自查并标 `ungrounded`。
    这是已知边界，不是已解决的问题。

## 12. 语料：体量、格式，以及「库这么小还要 RAG 吗」

这一节回答三个一定会被问到的问题，而且答案都在代码里能复现。

### 12.1 现状：确实小，小到全塞得下

| 项 | 实测 |
|---|---|
| 文件 | 22 个，**全是 txt**，合计 54 KB |
| 向量块 | **145 块**，平均 136 字，**总 19,789 字** |
| 换算上下文 | 约 **1.3 万 token**，占 128K 窗口的 **10%** |

所以"你库这么小，全塞进上下文不就行了"是个必须正面回答的问题，不能绕。

### 12.2 实测：全塞 vs 检索（`scripts/ab_fullcontext.py`）

同一模型（deepseek-chat）、同一提示词、48 题，唯一变量是上下文来源：

| 臂 | 得分 | 单题耗时 | 上下文 |
|---|---|---|---|
| A 全塞（19,789 字全给） | **0.9583** | 0.84 s | 20,276 字 |
| B 检索（混合检索 + 重排 top-5） | **1.0000** | 0.80 s | **351 字** |

两个结论，一个是意料之中，一个是意料之外：

- **成本差 57.8 倍，延迟几乎一样**（0.84 vs 0.80 s）。DeepSeek 的 prefill 很快，
  所以"全塞更慢"这个想当然的论据不成立，别拿它当理由。
- **全塞准确率反而低 4.2 个点，丢的正是 T031/T032「住在哪个省」。**
  原因不是"看漏了"，而是**原文里根本没有"江苏"两个字**：资料只写"住在南京"，
  正确答案靠 `(城市)-[:属于]->(省)` 这条图谱边推出来。检索链路把这条隐含事实
  显式写进了上下文，全塞做不到——它只能看到字面。

这就是这个项目对"小而全塞"最硬的一版回答：**检索不只是压缩上下文，
它还在做证据构造**。全塞把 145 个块原样喂进去，等于把"从哪推"这件事交还给模型，
模型的选择是不推。

### 12.3 体量真涨上去会怎样

用项目自身 10 个文档（184 KB）加多格式样本建了第二套索引：

```
965 块 / 123,787 字（约 7.7 万 token，占 128K 的 61%）
全塞单题 1.30 s（小库 0.84 s），输入成本 6 倍
```

也就是说**再扩 1.7 倍就撞上窗口上限**，而那时成本已经是每问 7.5 万 token。
全塞不是"错"，是**不可扩展**：它能撑到 20 万字，撑不到 200 万字，
而检索路线在 20 万字和 200 万字上用的是同一套代码。

### 12.4 多格式：PDF / 扫描件 / 图片

原来 `build_knowledge_base.py` 里有个 `PyPDFLoader` 分支，**从来没跑过**。
实测一页扫描件：

```
页数: 1
  第1页 抽取文字长度 = 0 字
```

不报错、不告警，静默产出空文档——这比"不支持 PDF"更糟：文件在库里，
问它永远答不出来，而且没有任何信号。

新增 `ingest/` 包（独立模块，**不接线到生产链路**）：

| 文件 | 职责 |
|---|---|
| `ingest/clean.py` | 页眉/页脚/页码去噪（跨页统计 + 数字归一化）、PDF 硬换行接回、空白规范化 |
| `ingest/loaders.py` | txt/md/pdf/docx/图片；PDF 表格走 pdfplumber 转 markdown；无文字层的页自动 OCR 兜底；**空页带 `empty` 标记，绝不静默丢** |
| `ingest/chunker.py` | 按标题分段、表格整块保留（超长表格切分时**每块重复表头**）、每块带 `heading_path` |

三个设计约束，都是踩出来的：

1. **页眉去噪必须做数字归一化**。`第 1 页` 和 `第 2 页` 逐字比较是两个不同的行，
   永远凑不够频次阈值。但归一化只能对**短行**做——长行里的数字是内容本身
   （"第 1 季度营收 128 万" vs "第 2 季度 143 万"），一起归一化会把两段正文
   判成同一行然后一起删掉。
2. **表格不能被压平**。pypdf 抽出来是 `菜系口味特点代表菜川菜麻辣鲜香…`，
   表头和数据糊成一行，等于这张表不存在。现在用 pdfplumber 取单元格，
   拼成 markdown；同时把压平的那行删掉，避免同一张表进库两遍。
   删的时候**按整行拼接去重，不按单元格**——第一版按单元格删，
   把正文标题里的「菜系」「代表菜」各删了一次，"主要菜系对照表" 变成了 "主要对照表"。
3. **OCR 与图像理解走注入**（`ocr=` / `caption=` 两个函数参数）。
   缺 tesseract 时只跑 caption；测试里塞假函数，不为测一行逻辑装系统级 OCR。

实测效果（`scripts/probe_ingest.py knowledge_base_v2 --ocr`）：

```
[NEEDS_OCR,OCR] q3_jianbao_scan.pdf:p1  chars=92
    2026 年第三季度经营简报 / 营业收入 1284300 元，同比增长 18.4% / 毛利率 42.7% …
[ok] caixi_duizhao.pdf:p2              chars=135
    主要菜系对照表下表按口味与代表菜对照… / | 菜系 | 口味特点 | 代表菜 | / | 川菜 | 麻辣鲜香 | 开水白菜 |
```

扫描件救回来了，页眉页码没了，表格变成 markdown，而且**正文一个字没被误删**。

### 12.5 附带结论：混合检索不是"两路一定更好"

> **2026-11-12 补记**：下面这组数字只有 **5 条**样本。后来在 88 条问题上重做
> （见 12.8），**"重排把顺序修对"这条没能复现**——重排在块级口径下基本不改召回。
> 这 5 条保留原样，是留个教训：5 条样本足以让你相信一个错的结论。

在第二套索引上问 5 个跨格式问题（`scripts/check_v2_retrieval.py`），
分别只看 top-3 是否命中预期文件：

| 检索方式 | 命中 |
|---|---|
| 纯向量 | **2/5** |
| 纯 BM25 | **5/5** |
| 混合 RRF（等权） | **4/5** |
| 混合 + bge-reranker | **5/5** |

三个反直觉的地方：

- **纯向量在 OCR 文本上很弱**。图表识别出来是 `402000, 431000, 451300` 这种碎片，
  语义向量抓不住"哪个月最高"；关键词反而一命就中。
- **等权 RRF 会被差的那一路拖累**，4/5 比 BM25 单路还低。融合不是免费的午餐，
  两路质量差距大时，弱的那路在投票。
- **重排才是把顺序修对的那一环**。它救回的就是 E5 那条：候选都在，
  只是顺序不对——这正是 reranker 该干的活。

### 12.8 规模曲线：145 块 → 3.2k 块

这一节回答的是 **"语料涨上去会怎样"**，也是 12.1 那个问题的另一半：
145 块时检索当然好用，问题是它能不能撑。

### 语料从哪来的（这段必须诚实）

| 来源 | 文件 | 块 | 性质 |
|---|---|---|---|
| `knowledge_base/` | 22 个 txt | 133 | **真实**业务语料（48 题基线用的就是它） |
| 仓库根 `*.md` | 8 篇 | 824 | **真实**项目文档（README/CASE_STUDY/OPS…） |
| `knowledge_base_v3/` | **838 个**（md/txt/pdf/docx/png/纯图像扫描件） | **3,063** | **合成**，`scripts/gen_corpus_v3.py` 生成 |

合成的原因很具体：**这台机器只通 PyPI**，维基、GitHub、Gitee 全部 15 秒超时，
下不到公开中文语料。

合成语料的价值在于**结构真实**，不是文字真实：每个客户有独立对接人、每份合同有
独立金额、每个型号有独立吞吐量，跨文档能串起来——所以"检索到错的那一份"是
**能被判出来**的；把同一句话复制几百遍的假语料做不到这一点。

它**不能**用来宣称业务准确率。真实语料只有那 22 个 txt 和 8 篇项目文档，
这一点在答辩时要说在前面，别等对方问。

### 实验设计（最容易做错的地方）

第一版我直接"取前 N 块"，结果曲线是**往上走**的（0.317 → 0.646）——
因为 N 变大时金标文件才逐渐进库。那不是检索变强，是题目变简单。

正确做法是**锚点固定，只加干扰项**：

- 锚点 = 88 条问题里所有含答案的块（共 121 块），每个规模点都完整保留
- 干扰项 = 其余块，按顺序取 `N − 121` 个
- 于是"5 个槽位要跟多少干扰项抢"成了唯一变量

第二个坑：**金标要细到块，不能细到文件**。按文件算时，`test5.txt` 的第 1 块
讲的是"他在杭州做后端"，被向量排进 top-5 就记成功，可答案在第 3 块——
重排按块打分反而"把命中挤掉"，我因此得出过"重排让召回从 0.840 掉到 0.691"
的错误结论。改用块级金标后重排恢复中性。

第三个坑：**真实题的金标不能用 `expected_source`**。那个字段已经过期——
T012「北京烤鸭的挂炉和焖炉」写的是 `test11.txt`，语料里实际叫 `kaoya.txt`。
48 题打分从来只看 `must_contain` 关键词，没有任何一处读过这个字段，所以当年
改语料时它烂了也没人发现。现在改成用 `must_contain` 反查语料（41/48 条可定标）。

### 结果（`scripts/scale_curve.py`，块级 recall@5）

| 语料块数 | 干扰项 | 向量 | BM25 | 混合 | 混合延迟 | top-5 上下文 |
|---|---|---|---|---|---|---|
| 300 | 180 | 0.469 | 0.753 | **0.790** | 0.45 ms | 766 字 |
| 500 | 380 | 0.432 | 0.765 | 0.778 | 0.62 ms | 761 字 |
| 1,000 | 880 | 0.346 | 0.790 | 0.741 | 1.10 ms | 757 字 |
| 2,000 | 1,880 | 0.321 | 0.667 | 0.679 | 2.53 ms | 731 字 |
| 3,229 | 3,109 | 0.284 | 0.593 | **0.642** | 4.22 ms | 686 字 |

（曲线跑到 3,229 块；服务里那套索引是 3,196 块——项目文档在两种建库顺序下
标题归属略有不同，差 1%，不影响结论。）

逐条给 10 个候选做重排（`--rerank`）：300 块 **0.790 → 0.753**（反而低 3.7 个点）、
3,229 块 **0.642 → 0.642**（持平）。每题多花 **114–160 ms**，是检索本身
（0.5–4.6 ms）的 **30 倍以上**。

**重排在这个口径下不加召回，甚至略伤。** 那它为什么还在链路里？因为拒答门槛用的
是它的分（见结论 2），不是因为它能提召回。

三个能直接说出口的结论：

1. **召回随规模单调下降**（0.790 → 0.642），掉得最狠的是纯向量（0.469 → 0.284），
   BM25 更抗跌（0.753 → 0.593）。**混合检索不是锦上添花，是规模上去之后的兜底**——
   这句话现在有数据支撑，不再是口号。
2. **重排的作用被高估了**。它把 top-10 重新排序，但召回（top-5 里有没有答案块）
   几乎不变；它真正不可替代的地方是**给拒答门槛一个可比分数**：
   `RAG_MIN_RELEVANT=0.15` 判的就是 rerank 分，越界问题 top1 只有 0.0026–0.0535、
   正常问题 ≥0.60，中间空档是它提供的。把重排理解成"提升召回"会做错优化方向。
3. **成本结构反直觉**：检索本身从 0.45 ms 涨到 4.22 ms（约 10 倍），但绝对值仍然
   可以忽略；真正的开销在重排，且**线性于候选数**。所以"扩语料"要担心的是
   重排窗口，不是向量检索。

### 顺手修掉的两个"规模相关"缺陷

这两个都是**把索引切到 3,196 块之后才暴露**的，145 块时看不见：

| 缺陷 | 症状 | 修法 |
|---|---|---|
| `RAG_RERANK_CANDIDATES=10` 太小 | 正确块常排第 11–20 名，被截在门外 → top1 只有 0.1096 → 低于 0.15 → 判"检索落空" → 拒答。**检索明明找到了** | `retrieval_policy.candidate_window()` 按规模分档：≤300 块仍是 10（生产行为不变），≤1000 块 16，更大 24 |
| 索引没有 `entity` 元数据 | 实体过滤 `filter={"entity": ...}` 得到空集 → 结果清成 0 块 → **全量拒答**（日志 `实体过滤后剩余: 0 个块`） | 启动时探测：`_index_has_entity_field()`。没有该字段就整体跳过实体过滤并告警；**判不出来时当作有**，保持旧行为 |

第二条还顺带解释了 v3 语料上端到端只有 0.583 的原因：那套索引**没有实体层**
（新语料没有实体词表、也没建图谱），240 份客户档案互相高度同构，纯靠
向量 + BM25 会串台。这反过来说明实体过滤不是装饰。

### 但这套合成语料测不了"真实语言"

0.583 这个数字要连着下面三条一起读，否则会得出错误结论：

1. **缺实体层**：240 份客户档案同构，只有公司名不同，过滤层一关就串台。
2. **模板措辞重复**：生成器里 `PHRASE_OPEN` / `PHRASE_NOTE` 那几句在 838 份
   文档里反复出现，把"差异化内容"稀释掉了。实测「IVS-2300 的额定吞吐量」，
   10 个候选的 rerank 分是 **0.129 / 0.119 / 0.035 / 0.032 …** ——
   **全部低于 0.15 门槛**，于是判"检索落空"。而同样的问题在真实语料里
   是 0.99 级别。这不是检索坏了，是语料的语言分布不真实。
3. **表格块被长文本块挤掉**：参数表那一块（`| 额定吞吐量 | 1799 件/小时 |`）
   在向量里排第 4，但在"k=10 候选 → 重排 → 取 5"里被概述块挤出前五。

所以：**这套语料能压规模、能测"规模对检索的压力"（12.8 的表就是干这个的），
但测不出"真实业务上的检索质量"**。要拿它当上线依据，必须换成真实文档重新标注。
把 0.583 说成"系统在 3000 块语料上只有 58 分"是错的，说成"没问题"更是错的。

### 12.9 换成真实中文语料：52 部法律 / 4,703 块

12.8 的语料是**合成的**，它只能证明"规模上去后检索会变差"，证明不了"检索质量
到底行不行"——生成器里那几句模板措辞在 838 份文档里反复出现，把区分度稀释掉了
（实测「IVS-2300 的额定吞吐量」10 个候选的 rerank 分全在 0.13 以下）。

所以补一套**真实语料**：

| 项 | 值 |
|---|---|
| 来源 | `github.com/LawRefBook/Laws`（法律法规公开文本） |
| 仓库规模 | 10,819 篇 md / 171.8 MB / 约 6,280 万字 |
| 取用 | 52 篇「企业合规知识库」常用法律，73.0 万字 |
| 切块 | 4,703 块（`.md` 4,570 + 企业语料 `.txt` 133） |
| 评测集 | `test_cases_law.json` 47 条，**由条文机械生成，不经过 LLM** |

**取数通道是这次新摸出来的**（这台机器上周还全部超时）：

```
github.com            200 / 0.79s
api.github.com        200 / 0.32s
codeload.github.com   200（tarball，43 MB，约 3 MB/s）
raw.githubusercontent 只解析到 IPv6 → 12 秒超时，不可用
```

所以走 `codeload` 的 tarball，不逐文件抓 raw。封装在 `scripts/fetch_laws.sh`。

**三条取舍，都是为了"答案可核验"**：

1. **同名多版本只留最新**。仓库里刑法有 16 个版本（1979→2023）、宪法 11 个、
   食品安全法 5 个。全收进来等于同一部法存十几份，检索会串台、金标会指到作废版本。
2. **已废止/被吸收的不收**。合同法、物权法、侵权责任法、婚姻法、继承法、民法总则
   已随民法典施行废止，收进来就是主动制造矛盾答案。白名单按名字匹配，天然挡住。
3. **不取 DLC 和部门规章全集**（那两堆 5,578 + 2,919 篇），否则 39 万块，
   这台 CPU 机器建不完也评测不动。

**评测集为什么能不用 LLM**：法条有稳定编号和唯一表述，问题可以反向构造——
`《专利法》第三十六条是怎么规定的？`、`《刑法》里的「毒品」是指什么？`、
`哪部法律规定，发明专利的申请人请求实质审查的时候？`、以及问不存在的条号（应拒答）。
判分关键词取**全库文档频率最低的 8 字片段**，再用 `scripts/check_cases_law.py`
逐条核验「这个关键词确实逐字出现在源文件里」，47 条全部通过。

实测（47 题，`eval_system.py --cases test_cases_law.json`）。**这是修复前的基线**：
定长 200 字切块 + `nomic-embed-text`（英文模型）。两条短板怎么修的见 12.10。

| 类别 | 题数 | 均分 | 检索召回 |
|---|---|---|---|
| 条文定位 | 16 | **0.938** | 1.000 |
| 主题定位 | 8 | 0.875 | 0.500 |
| 直接检索（企业语料） | 5 | 0.800 | 1.000 |
| **定义式** | 12 | **0.333** | 0.250 |
| 拒答（条号越界） | 4 | 1.000 | — |
| 跨主题 / 多跳 | 2 | 0.500 | 0.500 |
| 合计 | 47 | **0.745** | 0.663 |

**真实语料立刻暴露了三个合成语料看不见的缺陷**（都已修，都有单测）：

1. **来源全变成「未知来源」**。`rag_agent` 只读 `metadata["source"]`，而走 ingest
   管线建的多格式索引写的是 `source_file` / `source_path`——只有最早那套 145 块
   手工灌入的索引才有 `source`。表现是：46 题返回的 sources 全是「未知来源」，
   评测"检索召回率"掉到 0.202，看着像检索崩了，其实是标签读错。
   修：`_doc_source()` 按 `source_file → source → source_path` 回退并取 basename。
2. **块正文里没有法名**。一条法条正文是「第三十六条　发明专利的申请人…」，
   52 部法律里都有「第三十六条」，纯向量/BM25 无从区分——实测问
   《专利法》第三十六条会召回民法典物权编、商标法、刑法。法名当时只躺在
   metadata 里，两个检索器和生成模型都看不见。
   修：切块时把标题路径拼进正文第一行（`_with_heading`），代价是语料从 72.5 万
   字涨到 86.9 万字。
3. **引用型问句不该交给语义重排**。「《专利法》第三十六条」除了法名和条号没有
   任何内容，cross-encoder 只能按"像不像法条"打分，top1 只有 0.4599 且全错。
   这类查询本质是精确匹配：法名定文件、条号定段落。
   修：`_exact_article_lookup()` 正则识别「《X》第 N 条」→ 按 `source_file` 过滤
   → 正文里找该条号。触发条件很窄（正则命中 + 文件存在 + 正文确实含该条号），
   任一条不满足就落回原检索；真实企业语料没有「第 N 条」结构，这条分支在生产库上
   永远不会触发。

**当时没修的两条短板**（都在 12.10 里修掉了，这里留原始描述和当时的判断）：

- **定义式只有 0.333**。「《反不正当竞争法》里的「商业秘密」是指什么」——文件
  找对了（sources 就是 反不正当竞争法.md），但定义所在的**那一段**没进 top-5：

### 12.10 定义式 0.25 → 0.75：两个「不报错、只变差」的根因

12.9 把短板归成一条"切块混条"。按这个方向改完，定义式从 0.333 只爬到 0.250
（更差了）。停下来复查，发现是**两个独立原因叠加**，而且两个都不报错：

#### 根因一：切块按字数装箱，不按条

定长 200 字装箱会把「第一条 立法目的」和「第二条 定义」塞进同一块，
向量的相似度被前半段稀释。法条自带编号，本来有明确语义边界。

改法：切块器先判文档是不是"按条组织"（正文里连续出现 ≥5 个 `第 N 条`），
是就以条号为**硬边界**，一条一块；超长条在句末断开后，续块重新带上
「法名 > 章 > 条」前缀——否则第二块只剩「（二）…」这种枚举项，等于废料。
非法律文档走原路径，**11/11 个文档逐字一致**（用 HEAD 版本对比过）。

代价：4,703 → **7,082 块**（法律 6,949 + 业务 133），平均每块 140 字。

#### 根因二：嵌入模型是英文的（主因）

`.env` 里是 `RAG_EMBED_MODEL=nomic-embed-text`——**英文**模型。同一道题实测：

| 模型 | 正确块余弦 | 无关块余弦 | 间距 |
|---|---|---|---|
| `nomic-embed-text` | 0.6921 | **0.7221** | **−0.0300**（排序是反的） |
| `bge-m3` | 0.6928 | 0.4828 | +0.2100 |

排序反了，检索必然落空 → 判"知识库没有相关内容" → 拒答。评测里只表现为
"定义式 0.250"，日志里一行错都没有。

**为什么一直没被发现**：两个模型都是 768 维，Chroma 只校验维度，混用完全"合法"。
所以补了一道**索引签名**（`index_meta.py`）：建库时把 `provider:model` 写进
索引目录的 `_embed.json`，加载时比对，不一致就 WARNING，`/health` 里能直接看到
`kb.embed` 与 `kb.embed_status`（`ok` / `mismatch` / `unknown`）。
老库没有签名为 `unknown`——那是"不知道"，不能当"不匹配"，否则一上线满屏告警。

#### 顺手修掉的第三个 bug：窗口被 `.env` 覆盖，自适应从没生效

12.9 加了 `candidate_window()` 按规模放大重排窗口，但代码是
`os.environ.get("RAG_RERANK_CANDIDATES") or candidate_window(...)`——
`.env` 里写着 10，环境变量永远为真，**自适应窗口一次都没生效过**。
日志一直是 `rerank 候选截断: 20 → 10`，等于白加。

改成 `rerank_window(规模, 环境变量)`：**规模下限是地板，环境变量只能往上加**。
7,082 块现在真的是 24；生产 145 块 + `.env=10` 仍是 10，行为不变。
代价是重排耗时线性上涨：单题从 ~8 s 变成 **24.4 s**（CPU，2 vCPU）。

#### 结果：0.894，检索召回 1.000

| 阶段 | 均分 | 检索召回 | 改了什么 |
|---|---|---|---|
| 12.9 基线 | 0.745 | 0.663 | 定长切块 + nomic |
| 只改切块 | 0.766 | 0.651 | 按条对齐（召回没动，说明切块不是主因） |
| **再换 bge-m3** | **0.894** | **1.000** | 嵌入模型 + 窗口修复 |

分类（47 题）：

| 类别 | 题数 | 均分 | 检索召回 |
|---|---|---|---|
| 主题定位 | 8 | **1.000** | 1.000 |
| 直接检索（企业语料） | 5 | **1.000** | 1.000 |
| 跨主题 / 多跳 | 2 | **1.000** | 1.000 |
| 拒答（条号越界） | 4 | **1.000** | — |
| 条文定位 | 16 | 0.875 | 1.000 |
| **定义式** | 12 | **0.750** | 1.000 |
| 合计 | 47 | **0.894** | **1.000** |

**剩下的 5 题 0 分全部是"改写"，不是检索**——这一点很关键，别再去调检索：

| 题 | 判分关键词 | 模型实际写的 |
|---|---|---|
| L013 | 纳税人**应当**依法办 | 纳税人**需要**依法办理 |

所以瓶颈已经从「检索找不找得到」变成「生成时会不会照抄原文」。
要再往上，得在提示词侧要求法条类问题**原文引用**，而不是继续动检索参数。
